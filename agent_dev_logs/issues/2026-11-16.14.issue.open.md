# [\#14 Issue](https://github.com/ufal/atrium-ocr-postprocess/issues/14) `open`: Record builder: the ATR's docproc — reading order and blocks across pages
**Labels**: `enhancement`, `development`, `integration`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-11-16 14:51](https://github.com/ufal/atrium-ocr-postprocess/issues/14):

The builder reads docproc since #11–#13, but orders blocks by `readingOrder` only and ignores the rest of the structure the ATR gives. Ronald @rharasim will share real ATR outputs soon; they become the acceptance set.

- **Order within a page:** footnotes and sidebars (`readingOrderRole`, `readingOrderExtensions`) after the body; a caption next to its figure or table (`parentBlockId`); a figure's OCR child (`.t0`) right after it. The scoring passes read neighbouring lines, so the order also changes categories.
- **Blocks across pages:** read `continuedFrom`/`continuedTo`; lines stay on their pages, `content.text` joins the passage and rejoins a hyphenated word.
- `content.text` gets a blank line between blocks and pages.
- A table without `cellGrid` gives one line per row from its HTML or pipe content.
- Fixtures with continuations, roles, running headers and two columns; then the real samples.

Out of scope: ALTO; any layout in the record (**D26** - _The layout lives in docproc; the record links lines to blocks_)

ALTO input standard gets changed to docproc JSONs by default, but the developed functionality for various input formats remains as is; only the documentation will change slightly to shift the focus away from typical OCR formats.
